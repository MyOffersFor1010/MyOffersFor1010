0. EXECUTIVE SUMMARY
================================================================================

The project is a static, framework-free Progressive Web App (HTML + CSS + vanilla
ES-module JavaScript) for exactly TWO people. It provides real-time 1-to-1 text chat,
WebRTC audio/video calls, presence, typing indicators, read receipts, "delete for
me / for everyone", a disguised ("My Offers") login with a decoy page, and coded,
content-free notifications. All data lives in Cloud Firestore. Access control is
enforced by a well-written firestore.rules file (UID allowlist + "single active
session" check). Three Cloud Functions exist to send content-free push messages.

Overall quality: HIGH for a personal project. The code is defensive, consistent,
well commented, and the security rules are strict and covered by an emulator test
suite. No XSS sink (innerHTML / eval / document.write) is used anywhere.

Most important findings:
  1. Background push notifications are DISABLED in the committed code:
     FCM_VAPID_KEY is an empty string (js/firebase-config.js:41). Even if the Cloud
     Functions are deployed, no device can register for push. Notifications today
     only appear while a page is open but not on screen (and on mobile that page is
     usually frozen by the OS). => Notifications do NOT reliably reach both users.
  2. Messages are stored as PLAINTEXT in Firestore (field "text"). There is no
     end-to-end encryption. Anyone with access to the Firebase/GCP project (owners,
     editors, a leaked service account, Google) can read every message.
  3. Authentication is email + password only (no MFA). A compromised password gives
     full read access AND the ability to permanently erase the whole history for
     both people (rules allow either member to delete any message - by design).
  4. App Check is disabled (APP_CHECK_SITE_KEY = '' in js/firebase-config.js:47).
  5. The camouflage ("My Offers") is undermined by public artefacts: the GitHub repo
     is named "PrivateChat", README.md (which explains the decoy and "tap the title
     5 times") is served by GitHub Pages next to the app, and the login page text
     says "space for exactly two people" (index.html).
  6. One functional bug of note: in js/chat.js, reloadChat() invalidates the
     "deleted messages" listener without re-creating it (details in Section 7).

No CRITICAL vulnerability (e.g. open database, data readable by strangers, XSS) was
found in the code. Several items depend on console settings and are Not Verified.

2.2 Login and authentication
--------------------------------------------------------------------------------
  How it works :
   - js/auth.js initLoginForm(): signInWithEmailAndPassword(). Wrong credentials
     (auth/invalid-credential, wrong-password, user-not-found, user-disabled...)
     open the decoy page (js/decoy.js) instead of an error. Network / rate-limit
     errors show a normal message.
   - After sign-in, isAllowedUid() checks the UID against ALLOWED_UIDS; non-listed
     accounts are signed out and shown the decoy.
   - js/auth.js watchAuth(): onAuthStateChanged; rejects non-allowlisted users.
   - Auth persistence = browserSessionPersistence (js/firebase.js:25): the sign-in
     lives in sessionStorage; closing the tab/app requires the password again.
   - "Forgot password?" calls sendPasswordResetEmail() and always shows a neutral
     message (no account enumeration).
  Files        : js/auth.js, js/decoy.js, js/firebase.js, js/app.js, index.html
  Firebase     : Firebase Authentication (Email/Password)
  Assessment   : WORKS. Real enforcement is server-side (firestore.rules isMember()).

2.3 Session management (single active session) and logout
--------------------------------------------------------------------------------
  How it works :
   - js/session.js getAuthTime(): reads the auth_time claim from the ID token.
   - claimSession(): writes sessions/{uid} = { authTime, updatedAt }. Rules only
     accept an authTime >= the stored one, so the newest login wins.
   - firestore.rules isActive(): EVERY data request must carry an auth_time equal
     to sessions/{uid}.authTime, so an older device is rejected immediately even
     with a valid token.
   - watchSession(): the old device sees the newer authTime, ends any call, signs
     out and reloads (js/app.js endSuperseded()) and shows "Your account was logged
     in on another device."
   - Restored-session guard: a localStorage "alive" timestamp is refreshed every
     30 s; a sign-in restored by the browser after >10 min of non-use is signed
     out (js/session.js isStaleRestore(), RESTORE_GRACE_MS).
   - Logout (js/app.js handleLogout()): confirmation dialog, hang up, remove the
     push token, mark offline, signOut(), location.reload() to clear memory.
  Files        : js/session.js, js/app.js, js/auth.js, firestore.rules (sessions/,
                 isActive()), tests/rules.test.mjs ("single active session")
  Firebase     : Auth, Firestore collection sessions/{uid}
  Assessment   : WORKS. Known limits (documented in README): two logins within the
                 same second share auth_time; a browser restart within 10 min keeps
                 the session; a modified old client may keep an already-open stream
                 (Not Verified).

2.4 One-to-one messaging (send / receive)
--------------------------------------------------------------------------------
  How it works :
   - Single shared conversation: conversations/main/messages/{messageId}
     (CONVERSATION_ID = 'main'; rules only allow 'main').
   - Sending (js/chat.js sendMessage() / writeMessage()): client-generated doc id,
     optimistic "pending" bubble, setDoc({ senderId, text, createdAt:
     serverTimestamp(), deleted:false }). Rules are create-only, so retries can
     never duplicate a message. Max 4000 chars, empty/whitespace blocked (client
     AND rules). Failed sends show an alert icon; tapping retries with the same id.
   - Enter sends / Shift+Enter newline on desktop; composer cleared synchronously
     to prevent double sends.
  Files        : js/chat.js, index.html (#composer), firestore.rules (messages)
  Firebase     : Firestore conversations/main/messages
  Assessment   : WORKS. Limitation: Firestore uses a MEMORY cache only, so a message
                 queued while offline is lost if the tab/app is closed before
                 reconnecting (UI shows it as "pending").

2.5 Real-time synchronization
--------------------------------------------------------------------------------
  How it works : One onSnapshot listener on the newest 30 messages
                 (js/chat.js subscribeLive(), includeMetadataChanges) plus a listener
                 for messages blanked by "delete for everyone" (subscribeDeletions()),

                 private markers, hiddenMessages, sessions and calls.
  Files        : js/chat.js, js/app.js, js/presence.js, js/calls.js
  Firebase     : Firestore real-time listeners
  Assessment   : WORKS* (see bug B-01 in Section 7 about subscribeDeletions after a
                 reload).

2.6 Message history and pagination

2.8 Online / offline status and last seen
--------------------------------------------------------------------------------
  How it works : js/presence.js startPresence() marks users/{uid}.state='online' and
                 lastActive=serverTimestamp(); a heartbeat every 60 s while the page
                 is visible; pagehide writes 'offline' (best effort); logout writes
                 'offline'. The peer is "online" if state=='online' AND lastActive is
                 < 150 s old by server-corrected time (describePresence()). Otherwise
                 "last seen ..." (js/ui.js formatLastSeen()). The header re-evaluates
                 every 15 s (js/app.js PRESENCE_REFRESH_MS).
  Files        : js/presence.js, js/app.js renderPeer(), js/ui.js
  Firebase     : Firestore users/{uid}
  Assessment   : WORKS* (approximate by design - Firestore has no onDisconnect).
                 A hidden tab stops heart-beating, so a user with the app open in a
                 background tab appears "last seen" after ~2.5 min.

2.9 Read receipts and delivery ticks
--------------------------------------------------------------------------------
  How it works : No per-message writes. Each user writes lastDeliveredAt (when peer
                 messages arrive in any open session) and lastReadAt (when the chat
                 is shown, the tab is visible AND focused). The sender's ticks compare
                 message createdAt with the peer's markers: pending (clock) -> sent
                 (check) -> delivered (double check) -> read (double check, cyan).
                 Writes are throttled to 1 per 2 s (trailing).
  Files        : js/presence.js markRead()/markDelivered(), js/chat.js
                 refreshUnreadAndReceipts(), messageStatus(), setPeerMarkers()
  Firebase     : Firestore users/{uid}.lastReadAt / lastDeliveredAt
  Assessment   : WORKS. Rules prevent future timestamps (no fake "read").

2.10 Typing indicator
--------------------------------------------------------------------------------
  How it works : notifyTyping() writes typing=true + typingAt (max every 3 s);
                 typing=false after 4 s idle, on blur, and on send. The peer shows
                 "typing..." only if typingAt is < 6 s old and the user is online.
  Files        : js/presence.js, js/chat.js bindUi(), js/app.js renderPeer()
  Firebase     : Firestore users/{uid}.typing / typingAt
  Assessment   : WORKS.

2.11 User profiles
--------------------------------------------------------------------------------
  How it works : users/{uid} holds displayName (1-40 chars, default = email prefix).
                 Editable in Settings -> profile form (js/presence.js
                 updateDisplayName()). Avatars are initials on a gradient derived
                 from the UID (js/ui.js paintAvatar()). No profile photos, no bio,
                 no phone number.
  Files        : js/presence.js, js/settings.js, js/app.js, js/ui.js
  Firebase     : Firestore users/{uid}
  Assessment   : WORKS (minimal profile).

2.13 Audio and video calls (WebRTC)
--------------------------------------------------------------------------------
  How it works : Firestore is the signalling channel (calls/{callId} with SDP offer /
                 answer; ICE candidates in callerCandidates / calleeCandidates, ids
                 0..99). States: ringing -> accepted -> ended/failed, or ringing ->
                 rejected/busy/cancelled/missed - transitions enforced by rules.
                 Features: 40 s ring timeout -> missed; stale ringing docs (>50 s)
                 auto-marked missed; busy; glare (simultaneous calls) resolved by
                 UID ordering; ICE restart on network change (max 5 per call, 30 s
                 grace); mute, camera on/off, camera switching, draggable self-view;
                 wake lock; data channel for mute/camera/hangup signals; audio-route
                 warning ("may play on loudspeaker"); call history (last 15);
                 "missed N calls while you were away" toast.
  Files        : js/calls.js, js/webrtc.js, js/permissions.js, css/calls.css,
                 index.html (#incoming-call, #call-screen), firestore.rules (calls)
  Firebase     : Firestore calls/ (+ subcollections), composite index, TTL policies
  Assessment   : WORKS* - STUN only (no TURN configured: ICE_SERVERS has only Google
                 STUN, TURN_CREDENTIALS_URL = ''), so calls will FAIL on symmetric
                 NAT / strict firewalls / some mobile carriers. Media is DTLS-SRTP
                 encrypted. Real-device behaviour Not Verified.

3.4 Firestore security rules - analysis (firestore.rules)
--------------------------------------------------------------------------------
  Strengths (verified by reading the rules and the test file names):
   - Deny-by-default; no recursive wildcard allow.
   - isMember(): UID allowlist of exactly two users.
   - isActive(): request.auth.token.auth_time must equal sessions/{uid}.authTime ->
     superseded sessions lose access immediately.
   - Strict schemas with keys().hasOnly() / hasAll() on every write.
   - Server time enforced (createdAt == request.time); future timestamps rejected.
   - Messages: create-only (no duplicates), senderId == caller (no impersonation),
     length 1..4000, only the sender may "delete for everyone" (blank).
   - Calls: complete state machine; terminal states immutable; only callee accepts;
     ICE restarts numbered and capped at 20; SDP size <= 100,000 chars.
   - ICE candidates: ids 0..99, create-only, shape validated, expiry <= 2 days.
   - Push tokens and private markers are owner-only.
   - Profiles cannot be deleted; sessions cannot be deleted.

  Weaknesses / observations:
   - R-1 conversations/main/messages: "allow delete: if isActive()" - either member
     may permanently delete ANY message, including the other person's (stated as an
     owner decision). Impact: account compromise => irreversible history wipe.
   - R-2 users/{uid}: legacy fields clearedAt / callsClearedAt are still writable on
     the PUBLIC profile, which the peer can read. The current app writes them to the
     private doc, but old values (if present) remain visible to the peer.
   - R-3 users/{uid}: no validation that state/lastActive/typing are consistent;
     a member could set typing=true permanently (harmless between two people).
   - R-4 No rate limiting (not possible natively in rules). A member (or attacker
     with a stolen password) could flood messages, costing reads/writes and pushes.
   - R-5 The allowlist is duplicated in 3 files; a mismatch fails closed (safe) but
     is a maintenance risk.
   - R-6 Every rule evaluation performs get(sessions/{uid}) => one extra billed read
     per request / listener start (documented in README; cost only).
   - R-7 Test suite exists (tests/rules.test.mjs, ~45 cases) but its execution and
     result were Not Verified in this audit.

4.2 Finding details
--------------------------------------------------------------------------------

S-01  Messages stored in plaintext; no end-to-end encryption           [HIGH]
  Description : conversations/main/messages/*.text holds the message as clear text.
                Encryption is only Google's in-transit (TLS) and at-rest encryption.
  Files       : js/chat.js writeMessage(); firestore.rules (messages)
  Impact      : Anyone with access to the Firebase/GCP project (project owners and
                editors, anyone who obtains console access or a service-account key,
                Google under legal process) can read the full history. Contradicts
                the "secret messaging" goal.
  Recommended : Client-side E2EE with Web Crypto (ECDH P-256/X25519 key agreement +
                AES-GCM), ciphertext-only fields, rules updated to accept them.
                See Section 6 and Phase 4.

S-02  Password-only authentication, no MFA                              [HIGH]
  Description : Only email + password protect the account. No second factor, no
                login alerts beyond the "logged in on another device" notice.
  Files       : js/auth.js, js/firebase.js
  Impact      : Phished / reused / guessed password = full read access to all
                messages and call history, plus ability to wipe everything (S-03).
                The single-session design at least makes takeover visible to the
                real user.
  Recommended : Upgrade to Firebase Authentication with Identity Platform and enable
                TOTP MFA (or passkeys); enforce strong unique passwords; optionally
                require recent sign-in (auth_time) for destructive actions.

S-03  Either member can permanently erase all messages                  [HIGH]
  Description : firestore.rules messages "allow delete: if isActive() &&
                conversationId == 'main'" lets either user delete any message,
                including the other person's. js/chat.js eraseMessagesForEveryone()
                and calls.js eraseCallHistory() do this in batches.
  Files       : firestore.rules (messages delete), js/chat.js, js/calls.js, js/app.js
  Impact      : Irreversible data loss caused by a compromised account, a mistake,
                or a malicious partner. No soft delete, no backup in the code.
  Recommended : If this power is not essential, restrict delete to the sender's own
                messages, or require both parties (two-step consent document), or
                use a soft-delete flag plus scheduled server cleanup; enable
                Firestore PITR / scheduled backups (console).

S-04  App Check disabled                                                [MEDIUM]
  Description : APP_CHECK_SITE_KEY = '' (js/firebase-config.js:47); initAppCheck()
                returns false.
  Files       : js/firebase-config.js, js/firebase.js
  Impact      : Any script (not only your web page) can call the Firebase APIs with
                the public config: credential-stuffing against Auth, quota abuse.
                Data is still protected by rules.
  Recommended : Register reCAPTCHA v3/Enterprise, set the site key, monitor, then
                enforce for Firestore (and Auth via Identity Platform).

S-05  API key / Auth console hardening Not Verified                     [MEDIUM]
  Description : The web API key is committed (expected). Whether it is restricted to
                the GitHub Pages origin, whether sign-up and self-deletion are
                disabled, and whether email-enumeration protection is on cannot be
                verified from code.
  Files       : js/firebase-config.js (key location; value redacted)
  Impact      : If sign-up is open, anyone can create accounts (no data access, but
                quota abuse / log noise). An unrestricted key can be reused elsewhere.
  Recommended : Verify console settings per README Steps 3, 10, 11.

S-06  Public repository and README undermine the camouflage             [MEDIUM]
  Description : Remote is github.com/asmandage/PrivateChat. GitHub Pages serves the
                repository root, so README.md (explains "PrivateChat", the decoy page,
                "tap the title 5 times", the data model), firestore.rules (contains
                both UIDs), functions/ and tests/ are downloadable next to the app.
                Repository visibility: Not Verified.
  Files       : README.md, firestore.rules, functions/index.js, tests/*, .nojekyll
  Impact      : Anyone who finds the URL can learn the app's real nature and how to
                exit the decoy. (Data remains protected by rules.)
  Recommended : Make the repo private (Pages on a private repo needs a paid plan) or
                deploy only the web files (e.g. Firebase Hosting or a separate Pages
                branch/folder without README/rules/functions/tests).

S-07  Peer-to-peer calls expose IP addresses                            [MEDIUM]
  Description : ICE_TRANSPORT_POLICY = 'all' and no TURN; ICE candidates (with
                public/private IPs) are written to Firestore and exchanged.
  Files       : js/firebase-config.js, js/webrtc.js, js/calls.js writeCandidate()
  Impact      : Each user learns the other's IP/approximate location; candidates sit
                in Firestore until client deletion or TTL (~24 h + TTL lag).
  Recommended : Add a TURN service with short-lived credentials and set policy to
                'relay' when IP privacy matters.

S-08  Call signalling not authenticated end-to-end                     [MEDIUM]
  Description : SDP offers/answers (with DTLS fingerprints) travel through Firestore.
                Nothing verifies that the fingerprint belongs to the peer.
  Files       : js/calls.js, js/webrtc.js
  Impact      : Someone with Firestore admin access could alter SDP and MITM a call.
                Media is otherwise DTLS-SRTP encrypted.
  Recommended : Once E2EE identity keys exist (Phase 4), sign the SDP fingerprint or
                show a short verification code in the call UI.

S-09  Content-Security-Policy limitations                               [MEDIUM]
  Description : CSP is a <meta> tag (index.html:9-20) because GitHub Pages cannot send
                headers. It cannot set frame-ancestors or report-uri. It allows
                style-src 'unsafe-inline' and connect-src https: wss: (any host).
  Files       : index.html
  Impact      : If an XSS were ever introduced, exfiltration to any HTTPS host would
                be allowed. No XSS was found today.
  Recommended : Host on a platform that sends real headers (Firebase Hosting) with
                frame-ancestors 'none', narrow connect-src to *.googleapis.com,
                *.firebaseio.com, fcmregistrations.googleapis.com, etc.

S-10  Login page and metadata reveal the app's purpose                  [MEDIUM]
  Description : After the rename commit, index.html still says "A My Offers space
                for exactly two people" (login), "chat, audio and video calling space
                for two" (meta description), "Access restricted to two accounts"
                (sidebar footer). The message-empty text reads "This conversation is
                Offers between the two of you" (find/replace artefact).
  Files       : index.html
  Impact      : Anyone seeing the login page or a link preview learns it is a private
                two-person chat, defeating the disguise.
  Recommended : Review all user-visible copy for the disguise; fix the broken
                sentences.

S-11  No server-side rate limiting / abuse controls                    [MEDIUM]
  Description : Rules cannot rate-limit; functions push on every message.
  Files       : firestore.rules, functions/index.js
  Impact      : A compromised account could flood messages/calls (cost, push spam).
                maxInstances: 2 limits function concurrency only.
  Recommended : Budget alerts (console), App Check, optional per-user write counters
                via a Cloud Function, or rules that require createdAt spacing using
                a per-user "lastSentAt" field.

S-12  Auth refresh token in sessionStorage                               [LOW]
  Description : browserSessionPersistence stores the Firebase user (incl. refresh
                token) in sessionStorage, readable by any script on the origin.
  Files       : js/firebase.js
  Impact      : Only exploitable together with an XSS (none found).
  Recommended : Keep XSS-free practices (textContent only - already followed).

S-13  Restored-session guard has a 10-minute window                       [LOW]
  Description : RESTORE_GRACE_MS = 10 min (js/session.js). A browser restart within
                10 minutes of last use keeps the user signed in.
  Recommended : Shorter grace or an app-level PIN/biometric unlock (WebAuthn).

S-14  Same-second double login                                           [LOW]
  Description : Two sign-ins in the same second get the same auth_time; both stay
                valid (documented in README).
  Recommended : Accept, or add a random session nonce stored with the session doc.

S-15  Legacy cleared markers readable by the peer                        [LOW]
  Description : users/{uid}.clearedAt / callsClearedAt still allowed by rules and
                read by js/app.js latestMarker() as a fallback; the peer can read them.
  Recommended : Migrate and remove these fields from validUser().

S-16  Allowlist duplicated in three files                                [LOW]
  Files       : js/firebase-config.js, firestore.rules, functions/index.js
  Recommended : Single source (e.g. a config doc readable by rules, or custom claims).

S-17  Clickjacking protection is JavaScript-only                         [LOW]
  Description : js/theme-boot.js frame-buster; no X-Frame-Options / frame-ancestors.
  Recommended : Use a host that sends frame-ancestors 'none'.

S-18  Client storage contents                                            [LOW]
  localStorage : privatechat.prefs (theme, sounds, notify toggle, device ids),
                 privatechat.alive (timestamp), privatechat.pushTokenId (SHA-256 of
                 FCM token).
  sessionStorage: Firebase Auth user/session, privatechat.superseded flag.
  IndexedDB    : privatechat-notify (coded notification texts).
  No passwords, message content or private keys are stored. Device IDs and notify
  codes are mildly sensitive only. Risk: Low.

S-19  Superseded client with an open stream                              [LOW]
  Documented in README §8: a modified old client might keep receiving an already
  open listener until reconnect. Not Verified (needs emulator/live test).

S-20  No lock files                                                      [LOW]
  functions/ and tests/ have no package-lock.json -> non-reproducible installs,
  supply-chain drift. Recommended: commit lock files.

S-21  Old SDK version                                                    [LOW]
  Firebase JS SDK 10.12.2 pinned in all imports and sw.js. Not insecure per se, but
  should be updated periodically (all URLs + SDK_CACHE in sw.js together).

S-22  Unicode control characters not filtered                            [LOW]
  Message text and displayName accept any Unicode (incl. RTL override). Rendering is

S-23  Deleted message text in backups                                    [LOW]
  "Delete for everyone" blanks the text in place. Whether PITR / backups are enabled

4.3 Checks performed with NO issue found
--------------------------------------------------------------------------------
  - XSS / unsafe HTML: no innerHTML, outerHTML, insertAdjacentHTML, eval,

5.1 Architecture as implemented
--------------------------------------------------------------------------------
  Path A - In-page notifications (no server needed)
    js/notifications.js notifyPrivate(kind) is called by:
      chat.js handleIncoming()  -> 'm'  (new message)
      calls.js showIncoming()   -> 'a' / 'v' (incoming audio/video call)
      calls.js announceMissed() -> 'mc' (missed call)
    Conditions: permission granted AND Settings toggle on (prefs.browserNotify) AND
    document NOT visible AND background push NOT active on this device.
    Display: ServiceWorkerRegistration.showNotification() (fallback: new
    Notification()). Text = coded title/body from IndexedDB (notify-config.js).

  Path B - Background push (FCM + Cloud Functions)
    1. js/push.js enablePush(): getToken(messaging, { vapidKey, serviceWorkerRegistration })
       -> users/{uid}/pushTokens/{sha256(token)} = { token, authTime, updatedAt }.
    2. functions/index.js on Firestore triggers:
         notifyNewMessage   (messages create)          -> { k:'m' },  TTL 24 h
         notifyIncomingCall (calls create, ringing)    -> { k:'a'|'v' }, TTL 40 s
         notifyMissedCall   (calls ringing->missed/cancelled, not collision/stale)
                                                       -> { k:'mc' }, TTL 24 h
       Pushes go only to tokens whose authTime == sessions/{uid}.authTime.
       Data-only message, Urgency high, Topic header pc-<kind> (collapses queue).
       Dead tokens are deleted.
    3. sw.js 'push' handler: reads kind, skips if an app window is visible (except
       Safari, which must show every push), reads codes from IndexedDB, shows the
       coded notification with tag pc-m / pc-c / pc-mc and renotify.

5.3 Can notifications reliably reach both users today?
--------------------------------------------------------------------------------
  NO. With the committed configuration:
   - Notifications appear only if the receiving user has the app OPEN (tab or
     installed window) but NOT on screen, has turned the Settings switch ON and has
     granted permission.
   - On phones, a backgrounded browser/PWA is suspended within minutes, so messages
     and calls received later produce NO notification until the app is reopened.
   - When the app/browser is closed, nothing is delivered.

  What is missing to make it reliable:
   1. Generate the Web Push (VAPID) key pair and set FCM_VAPID_KEY.
   2. Blaze plan + deploy functions/ with REGION matching the Firestore location.
   3. If the API key is restricted, allow Firebase Installations API and FCM
      Registration API.
   4. Each user enables the Settings switch on each device (token registration).
   5. Android: allow notifications and set battery to "unrestricted"; iOS: install
      to Home Screen.
   6. Optional: notificationclick should focus/open the app (clients.openWindow) -
      still privacy-safe because it opens the login screen.
   7. Optional: periodic token re-validation / cleanup of stale token docs.
   8. Web limits remain: no ringing full-screen call UI when closed (needs a native
      wrapper with ConnectionService/CallKit).

  | Hidden notification previews         | YES         | Already content-free (coded texts). |
  | Disappearing messages                | NO          | No expiry field / TTL for messages. |
  | Private conversations                | PARTIAL     | Only 2 allowlisted users; single    |
  |                                      |             | conversation 'main'; no per-chat    |
  |                                      |             | lock or hidden chats.               |
  | Screen privacy (no content in title, | YES         | Neutral titles, decoy login,        |
  | decoy)                               |             | memory-only cache.                  |
  +--------------------------------------+-------------+-------------------------------------+

6.2 Architectural fit (what helps, what blocks)
--------------------------------------------------------------------------------
  Helps:
   - Exactly two parties and one conversation -> simple pairwise key agreement
     (no group key management).
   - Cloud Functions never read message text (only msg.deleted / senderId), so they
     are already compatible with ciphertext.
   - Notifications are already content-free.
   - All rendering is centralised in chat.js updateNode() / updateSidebarPreview(),
     so decryption can be inserted in one place (toMessage()).
   - Web Crypto is already used (push.js sha256Hex) and available in all targets.
   - Memory-only Firestore cache: decrypted plaintext never touches disk.

  Blocks / must change:
   - firestore.rules messages: keys().hasOnly(['senderId','text','createdAt','deleted'])
     and text.trim().size() > 0, <= 4000. Ciphertext needs new fields (e.g. ct, iv,
     v, keyId) or base64 in 'text' (4000 chars => about 2,900 bytes of plaintext).
   - users/{uid} validUser() hasOnly(...) forbids storing a public key; a new path
     such as users/{uid}/keys/{keyId} with rules is required.
   - Session-only login model: a private key must survive between logins. Options:
       a) non-extractable CryptoKey in IndexedDB per device (conflicts with "nothing
          left on device"), plus device-linking flow; or
       b) private key wrapped with a key derived from a separate passphrase
          (PBKDF2/Argon2) and stored in Firestore; unwrapped in memory at login
          (works across devices, fits the session-only design).
   - "Delete for everyone" blanking still works; sidebar preview and unread logic
     need the decrypted text.
   - Message search (if added later) cannot run server-side.
   - Disappearing messages: needs an expiresAt field (rules), a Firestore TTL policy
     on messages (deletion lag up to ~24 h, so the client must also hide expired
     messages), and a decision on behaviour for older pages already in memory.
   - Pagination/ordering stays on server createdAt (not encrypted) - acceptable
     metadata leak; senderId and timestamps remain visible to the server.

6.3 What would need to be added (no implementation done)
--------------------------------------------------------------------------------
  1. Identity key pair per user (ECDH P-256 or X25519 where supported) + signing key.
  2. Public key publication path + rules; key fingerprint verification UI
     (safety number / QR) to detect key substitution by a server admin.
  3. Private key protection (passphrase-wrapped backup or per-device keys).
  4. Message encryption: AES-256-GCM with a per-message random IV; key derived via
     HKDF from the ECDH shared secret (optionally a ratchet for forward secrecy).
  5. New message schema + rules (ct, iv, v, keyId), migration plan for existing
     plaintext (either leave, re-encrypt by owner, or erase).
  6. Disappearing messages: expiresAt + TTL policy + client hide + rules.
  7. Optional app lock (PIN/WebAuthn) before showing decrypted content.
  8. Signed SDP fingerprints for calls (S-08).

7.1 Functional bugs / potential runtime issues
--------------------------------------------------------------------------------
  B-01  [Medium] Deleted-messages listener goes inert after a reload
        File/func : js/chat.js subscribeDeletions() (~line 151), reloadChat() (~723)
        Detail    : subscribeDeletions() captures `gen = generation` and ignores
                    events when gen !== generation. reloadChat() does generation++
                    and re-subscribes only the live listener, NOT the deletions
                    listener. After any reload (clear-for-me, peer's "delete for
                    everyone" wipe, clearedAt change), "delete for everyone" on
                    messages outside the newest-30 window no longer updates live,
                    while the listener keeps running (and costing reads).
        Effect    : Older loaded bubbles keep showing text the sender deleted until
                    the next app load.

  B-02  [Low] Double reload / transient filtering after "delete for me"
        File/func : js/presence.js watchPrivateMarkers() ('estimate' timestamps),
                    js/chat.js setClearedAt()
        Detail    : The first snapshot carries a locally estimated clearedAt, the
                    second the server value -> reloadChat() runs twice. The estimate
                    uses the device clock (not serverNow), so with a fast device
                    clock new messages could be hidden briefly.

  B-03  [Low] Offline sends are lost on close
        File      : js/firebase.js (memoryLocalCache), js/chat.js
        Detail    : Pending writes live in memory only. Closing the app while
                    offline silently drops "pending" messages.

  B-04  [Low] "last seen" uses device clock
        File/func : js/ui.js formatLastSeen() uses Date.now(), while
                    presence.js describePresence() uses serverNow(). With clock skew,
                    "last seen 3 min ago" can be wrong or negative ("just now").

  B-05  [Low] No OS notification when the desktop window is visible but unfocused
        File/func : js/notifications.js notifyPrivate() - returns when
                    visibilityState === 'visible', although chat.js treats the chat
                    as inactive when !document.hasFocus().

  B-06  [Low] Possible screen race for non-allowlisted accounts
        File/func : js/auth.js initLoginForm() submit handler vs watchAuth()
        Detail    : Both sign the user out; watchAuth shows the login screen with
                    "This account is not authorized..." while the submit handler
                    shows the decoy. Final screen depends on callback order (Not
                    Verified at runtime). If the user exits the decoy, the hidden
                    error text reveals the real app.

  B-07  [Low] Retry after an unknown-outcome send
        File/func : js/chat.js onOwnBubbleClick() / writeMessage()
        Detail    : If a setDoc actually committed but the client saw an error, the
                    retry is an update -> permission-denied -> bubble stays "failed"
                    although the message exists (the live snapshot would then show
                    it as sent; minor confusion only).

  B-08  [Low] Nested modal focus / Escape handling
        File/func : js/ui.js openModal()/closeModal() (single lastFocus/openModalEl)
        Detail    : A confirm dialog opened over Settings overwrites lastFocus and
                    openModalEl; after it closes, Escape no longer closes Settings and
                    focus may be lost. Accessibility issue only.

  B-09  [Low] Camera switch failure can drop video
        File/func : js/webrtc.js switchCamera()
        Detail    : The old track is stopped before acquiring the new one; if both
                    getUserMedia attempts fail, the call continues without video.
                    (Intentional for phones that cannot open two cameras.)

  B-10  [Low] Push status depends on stale token docs
        File      : js/push.js, functions/index.js
        Detail    : Old token documents are never cleaned unless FCM reports them
                    dead. Harmless (not targeted), but accumulates.

  B-11  [Info] UI copy broken by the rename commit (ee705ce)
        File      : index.html - "This conversation is Offers between the two of
                    you", "A My Offers space for exactly two people", "My offers call
                    audio: ...", "My Offers notifications". See also S-10.

  B-12  [Info] Unused asset: assets/icons/favicon.svg (README marks it "old").

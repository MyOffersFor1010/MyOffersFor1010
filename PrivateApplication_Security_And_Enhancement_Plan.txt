0.1 Short summary
--------------------------------------------------------------------------------
Everything requested is feasible within the existing vanilla-JS + Firebase design,
with no framework and no new runtime dependency (all cryptography can use the
browser's built-in Web Crypto API; Firebase Storage uses the same pinned Firebase
SDK 10.12.2 from gstatic). The work splits into seven phases (Section 16):

  Phase 0  Preparation and decisions (console work, backups, Blaze plan)
  Phase 1  Disguise: public homepage, member-style decoy, neutral text, repo/hosting
  Phase 2  Reliable private notifications + safe notification click
  Phase 3  Security hardening (App Check, MFA, headers, sessions, backups)
  Phase 4  End-to-end encryption of text messages (+ migration of old messages)
  Phase 5  Encrypted photo sharing via Firebase Storage
  Phase 6  Finalisation (encrypted-only rules, removal of legacy paths, docs)

Notifications are your top priority and depend mostly on configuration. The single
largest blocker is that FCM_VAPID_KEY is empty in production (verified below), so
background push has never been able to work.

  NEW findings from this pass (not in the audit):
   N-1  Root cause of the notification-click complaint: sw.js 'notificationclick'
        only calls event.notification.close(). It never focuses or opens the app.
        The in-page fallback (new Notification(...) in js/notifications.js) has no
        click handler at all. This was a deliberate "tap = dismiss" design.
   N-2  Duplicated browser tab = two simultaneously active sessions on one device.
        Chrome/Edge copy sessionStorage when a tab is duplicated, so the duplicate
        restores the same Firebase sign-in with the SAME auth_time. The
        single-session check (auth_time equality) cannot distinguish them, and the
        restore guard passes because the "alive" marker is fresh.
   N-3  The GitHub Pages URL itself contains "PrivateChat" (/PrivateChat/). It is
        visible in the address bar, browser history, and - for notifications from a
        non-installed browser tab on Android - in the notification header origin.
   N-4  The Firebase project ID starts with "privatechat-". It appears in the
        public config file, in every Firestore/Auth network request, in the
        authDomain and in the Storage bucket name. A project ID can NEVER be renamed.
   N-5  github.io origin is shared by all of your GitHub Pages project sites
        (asmandage.github.io/*). localStorage and IndexedDB of this app are
        readable by any other page you publish on that origin.
   N-6  Every message push triggers renotify:true, so a burst of messages makes the
        phone alert once per message (sound/vibration each time).
   N-7  Pre-login error texts can reveal internals: e.g. "Check the UID allowlist in
        firestore.rules" (js/ui.js friendlyError), "Setup required ... two authorized
        UIDs" and "PrivateChat failed to start" (js/app.js), "This account is not
        authorized to use this app." (js/auth.js).

0.3 Decisions required before implementation
--------------------------------------------------------------------------------
  D-1  Hosting / repository strategy (Section 5.5)
       a) Private source repo + Firebase Hosting on a neutral custom domain
          (RECOMMENDED: real security headers, no internals published).
       b) Private source repo + separate public "web-only" repo on GitHub Pages.
       c) Keep the current public repo (not recommended).
  D-2  Firebase project ID containing "privatechat-": accept (RECOMMENDED for now;
       visible only on technical inspection) or migrate to a new neutral project
       (large effort, Section 5.6).
  D-3  Notification tap when the app is ALREADY open and signed in:
       a) Show a neutral "privacy cover" (homepage look) that needs an unlock
          (RECOMMENDED; matches "must not open the chat directly").
       b) Just focus the existing window as it is.
  D-4  Push delivery model:
       a) Session-bound (current): only devices of the newest login receive pushes;
          logging in on a laptop silences the phone.
       b) Device-bound (RECOMMENDED): every device where the user enabled
          notifications keeps receiving content-free pushes until removed in
          Settings or until logout. Payload is content-free, so the risk is low.
       Also: should LOGOUT stop notifications on that device? (current: yes)
  D-5  "Delete conversation for everyone" by either member: keep, restrict to own
       messages, or keep with backups only.
  D-6  E2EE key protection: separate encryption passphrase (RECOMMENDED, required)
       + printed recovery code (RECOMMENDED) + optional "remember this device".
  D-7  Existing plaintext history: re-encrypt by each sender (RECOMMENDED), keep as
       "legacy unencrypted", or erase.
  D-8  Photo limits: max processed size (RECOMMENDED 5 MB), max photos per send
       (RECOMMENDED 10), output format (RECOMMENDED JPEG, PNG kept when transparent),
       allow "Save to device" in the viewer (default OFF - it writes a plaintext
       file).
  D-9  MFA: enable TOTP (authenticator app) via Identity Platform (RECOMMENDED) or
       stay password-only.
  D-10 Remove the secret "tap the title 5 times" decoy exit and replace it with an
       ordinary "Sign out" link (RECOMMENDED - a normal app has one, and no secret
       mechanism has to be kept hidden).

1. EXISTING ARCHITECTURE SUMMARY
================================================================================

  Client  : One static page (index.html) + 18 ES modules in js/ + 4 CSS files.
            No framework, no build. Firebase JS SDK 10.12.2 from www.gstatic.com.
  PWA     : manifest.json ("My Offers"), sw.js (network-first shell cache, push
            display, notification click = dismiss only).
  Auth    : Firebase Authentication, email/password, browserSessionPersistence
            (sessionStorage). Two allowlisted UIDs. Single active session enforced by
            firestore.rules (sessions/{uid}.authTime == token auth_time).
  Data    : Cloud Firestore with memory-only cache. Collections: sessions, users
            (+private/markers, hiddenMessages, pushTokens), conversations/main/
            messages, calls (+callerCandidates, calleeCandidates).
  Server  : functions/index.js - 3 Firestore-triggered Cloud Functions (v2, Node 22,
            us-central1) that send data-only FCM pushes { k: 'm'|'a'|'v'|'mc' }.
            Deployment NOT VERIFIED.
  Calls   : WebRTC with Firestore signalling, Google STUN only.
  Hosting : GitHub Pages, https://asmandage.github.io/PrivateChat/ (VERIFIED live).

  Boot flow today (js/app.js main()):
    boot spinner "Verifying your session..." -> watchAuth()
      no user  -> login screen ("My Offers", subtitle reveals two-person purpose)
      user     -> startSession(): claimSession -> startPresence -> listeners ->
                  initChat/initCalls -> app screen
    wrong credentials -> decoy deals page (js/decoy.js), exit by reload or 5 taps.

4.1 Target behaviour
--------------------------------------------------------------------------------
  Open site  ->  [Public homepage "My Offers"]  (ordinary deals site, "Sign in" button)
                       |
                 [Sign in sheet]  email + password
                  /                        \
     Firebase OK AND UID allowlisted     anything else (wrong password, unknown email,
     AND session claimed                 disabled account, valid-but-unlisted account)
          |                                         |
   [Real app] (chat, presence, calls)      [Member dashboard decoy]
                                            "Welcome back" - saved offers, points,
                                            recent orders, normal "Sign out" link.
                                            100% static. NO Firebase session, NO
                                            Firestore access, NO private module run.

  Ordinary errors stay ordinary (like any web shop):
   - invalid email format     -> "Enter a valid email address."
   - too many attempts        -> "Too many attempts. Try again later."
   - network offline          -> "You're offline. Check your connection."
  These do not reveal anything specific to this app. (Showing the decoy for
  "too many attempts" is NOT recommended: the real user would then see the decoy
  while typing the correct password, which is confusing.)

4.2 Security invariants (must hold after implementation)
--------------------------------------------------------------------------------
  I-1  The decoy never calls Firebase, never creates or fakes a session, never
       writes local storage that could later be mistaken for a sign-in.
  I-2  startSession() (private services: presence, chat, calls, push, E2EE) runs
       ONLY when: onAuthStateChanged reports a user, isAllowedUid(uid) is true,
       claimSession() succeeded (server accepted the auth_time) and the restore
       guard passed. This is already true today and must stay true.
  I-3  Any failure inside startSession() returns to the PUBLIC HOMEPAGE (not a
       technical error screen) and logs only an error code to the console.
  I-4  Firestore/Storage rules remain the real boundary; the client allowlist is
       cosmetic. The decoy is camouflage only.
  I-5  No URL, query string or fragment ever changes what is shown. The app is a
       single URL; state is never encoded in it.

  Reason          : N-2 (two live sessions with identical auth_time).

7. NOTIFICATION CLICK BEHAVIOUR
================================================================================

7.1 Current behaviour and root cause (VERIFIED)
--------------------------------------------------------------------------------
  sw.js:
     self.addEventListener('notificationclick', (event) => {
       event.notification.close();          // and nothing else
     });
  So tapping a notification on the phone closes it and does NOT open the app. The
  in-page fallback notification has no click handler at all.

7.2 Required behaviour
--------------------------------------------------------------------------------
  - Open or focus the installed app / website.
  - Land on the normal homepage / sign-in experience - never the chat directly.
  - No chat-specific URL, query, fragment, message ID or deep link.
  - Never bypass authentication; normal session checks still apply.
  - Reveal nothing after the click.

7.3 Planned design (C-03)
--------------------------------------------------------------------------------
  sw.js 'notificationclick':
    1. event.notification.close()
    2. event.waitUntil( async () => {
         const scopeUrl = self.registration.scope;          // e.g. https://host/  (no query/hash)
         const wins = await clients.matchAll({ type: 'window', includeUncontrolled: true });
         const mine = wins.filter(w => w.url.startsWith(scopeUrl));
         if (mine.length) {
           const w = mine[0];
           await w.focus();
           w.postMessage({ t: 'nc' });     // neutral, carries no data
         } else {
           await clients.openWindow(scopeUrl);   // plain scope URL only
         }
       })
    No notification 'data' field is read or written (stays empty).

  Page side (js/app.js, listener on navigator.serviceWorker 'message'):
    - Accept only messages from the active service worker with { t: 'nc' }.
    - If NOT signed in (fresh window, or after browser restart): nothing special -
      the normal homepage is shown; signing in follows the normal flow.
    - If signed in (window already open):
        D-3a (recommended): show the PRIVACY COVER = homepage look over the app.
             Unlock options (choose one): re-enter the account password
             (reauthenticateWithCredential - real server check), or after Phase 4
             the encryption passphrase/PIN (local). While covered, chat DOM is
             hidden (display:none), not just overlaid. Optional: same cover after X
             minutes hidden (auto-lock).
        D-3b: focus only, app shown as it was.

  Why this satisfies "do not bypass authentication": a fresh window always starts
  at the homepage and needs the password (session-only sign-in); an existing window
  is already authenticated, and with D-3a it is additionally locked behind the cover.

================================================================================
8. END-TO-END ENCRYPTION ARCHITECTURE
================================================================================

8.1 Goals and threat model
--------------------------------------------------------------------------------
  Protect message CONTENT (and later photos) from: Firebase/Google Cloud operators,
  anyone with project console access, a leaked service account, Firestore backups,
  and an attacker who knows only a Firebase login password.
  NOT protected: metadata (who/when, sizes, read times, presence, call logs), a
  compromised/unlocked device, malicious code served by the website itself (a web
  app can always be changed by whoever controls hosting - inherent to web E2EE),
  screenshots by the other user.

8.2 Primitive choice (no homemade protocol)
--------------------------------------------------------------------------------
  Use only standard primitives from the browser Web Crypto API (no new library):
   - Key agreement  : ECDH on NIST P-256 (universally supported; X25519 support in
                      browsers is still uneven).
   - Key derivation : HKDF-SHA-256 (RFC 5869).
   - Encryption     : AES-256-GCM (NIST SP 800-38D), 96-bit random IV, 128-bit tag.
   - Passphrase KDF : PBKDF2-HMAC-SHA-256, >= 600,000 iterations (OWASP guidance;
                      Argon2id would be stronger but needs a WebAssembly library).
   - Hash           : SHA-256 for fingerprints and attachment integrity.
  Construction = static-static Diffie-Hellman + KDF + AEAD, the same structure as
  NaCl/libsodium "crypto_box" and HPKE's authenticated mode. This is a well-known
  construction, not a new protocol.
  Trade-offs (be explicit):
   - No forward secrecy: if a private key AND stored ciphertext are both obtained,
     all messages under that key can be decrypted. Mitigation: key rotation epochs
     (8.7). Signal-style double ratchet would need a maintained library (none is
     officially supported for browsers) - out of scope.
   - Alternative with a dependency: libsodium.js (crypto_box / secretstream) - well
     audited, ~200 KB, adds a dependency. Not recommended given "no unnecessary
     dependencies", but acceptable if you prefer audited high-level APIs.
   - Recommendation: have the final crypto module reviewed by a second person.

8.3 Keys
--------------------------------------------------------------------------------
  Per user:
   - Identity key pair IK = ECDH P-256. keyId = first 16 hex chars of
     SHA-256(SPKI(public)).
   - (Phase 4b) Signing key pair = ECDSA P-256 for signing SDP fingerprints (S-08)
     and the key-change log.
  Conversation key (both users derive the same):
     shared = ECDH(myPriv, peerPub)                         (256 bits)
     salt   = SHA-256( sort(SPKI_A, SPKI_B) concatenated )
     CK     = HKDF-SHA-256(shared, salt, info = "mo/v1/main") -> AES-GCM-256,
              non-extractable CryptoKey, kept in memory only.
  Per attachment: a fresh random AES-256-GCM file key (Section 9).

8.4 Private key protection, backup and recovery (D-6)
--------------------------------------------------------------------------------
  Why a SEPARATE encryption passphrase (never the login password): the login
  password is sent to Firebase; anyone controlling Firebase could then derive the
  key. Also an email password reset would destroy access to all messages.
  Stored in Firestore users/{uid}/private/keyBackup (owner-only read):
     { v:1, keyId, kdf:'PBKDF2-SHA256', iter:600000, salt(16B), iv(12B),
       wrapped: AES-GCM( PBKDF2(passphrase), PKCS8(privateKey) ),
       rcIv, rcWrapped: AES-GCM( recoveryKey, PKCS8(privateKey) ) }
  - Recovery key: 128+ random bits shown ONCE as a printable code (e.g. 8 groups of
    4 characters). If BOTH passphrase and recovery code are lost, encrypted history
    is permanently unreadable (by design).
  - Unlock flow: after successful sign-in and session claim, a neutral "Enter your
    security code" screen; the private key is unwrapped into a NON-extractable
    CryptoKey held in memory; cleared on logout/teardown (page reload).
  - Optional "Remember this device" (D-6): store the non-extractable CryptoKey in
    IndexedDB (structured clone keeps it non-extractable). Trade-off: device theft
    + browser profile access = decryption without passphrase; conflicts with the
    "nothing left on the device" policy. Default OFF.
  - Brute-force resistance of the backup depends on passphrase strength: require
    >= 12 characters or 4+ random words; show a strength hint.
  - Never stored: passphrase, recovery code, raw private key, CK - in any storage
    or log.

8.5 Public key publication and verification
--------------------------------------------------------------------------------
  - users/{uid}/keys/{keyId}: { alg:'ECDH-P256', spki (Bytes), createdAt } -
    readable by both members, created only by the owner, immutable (no update/
    delete). Rotation = new keyId.
  - Safety number: SHA-256( sort(SPKI_A, SPKI_B) ), shown as 12 groups of 5 digits
    (and optionally compared during a call). Both users compare once.
  - Trust record users/{uid}/private/trust: { peerKeyId, verifiedAt, mac } where the
    record is MACed/encrypted with a key derived from the user's OWN private key, so
    a server-side attacker cannot forge "verified".
  - Key-change warning: if the peer's current keyId differs from the trusted one,
    sending is paused and a warning asks to re-verify.
  - Honest limit: until users compare safety numbers, a server-side attacker could
    substitute public keys (MITM). Verification closes this.

8.6 Message format (schema v2) and processing
--------------------------------------------------------------------------------
  conversations/main/messages/{messageId}
    { senderId, createdAt (server), deleted:false, v:2, kid, iv (Bytes 12), ct (Bytes) }
  Plaintext before encryption (JSON, then padded to a multiple of 256 bytes to hide
  exact length):
    { t:'text', body:'...' }                                  text message
    { t:'image', items:[ {fileId, thumbId, key, iv, tIv, sha256, tSha256, w, h,
                           mime, bytes} ] }                    photo message (Sec. 9)
  AAD (authenticated, not encrypted): "mo|v2|main|<messageId>|<senderId>|<kid>"
  -> ciphertext cannot be moved to another message/sender undetected.
  kid = "<keyIdA>.<keyIdB>" (sorted) identifies which key pair epoch was used.
  Changes in js/chat.js (Area D):
   - sendMessage()/writeMessage(): encrypt before setDoc (messageId already
     generated client-side - required for AAD).
   - toMessage(): decrypt (async; cache plaintext in the in-memory Map only); failed
     decryption -> bubble "This message can't be displayed" (+ reason in console).
   - updateSidebarPreview(), unread counter: use decrypted text.
   - deleteMessage() "for everyone": set ct = empty Bytes, iv = empty, deleted=true.
   - Max length: the 4000-char limit stays client-side; rules bound ct size.
  Firestore stores only ciphertext; the memory-only cache keeps plaintext off disk.

8.7 Key rotation
--------------------------------------------------------------------------------
  New identity key -> new keyId -> new kid for new messages. Old private keys stay in
  keyBackup (array "history", each wrapped) so history remains readable. Deleting an
  old private key = "crypto-shredding" of messages encrypted under it.

8.8 Migration of existing plaintext messages (D-7)
--------------------------------------------------------------------------------
  Step 1  Deploy dual-mode rules (accept v1 plaintext AND v2 encrypted).
  Step 2  Both users set up keys (app prompts after sign-in).
  Step 3  Client sends v2 only when BOTH public keys exist; otherwise blocks sending
          with a "waiting for the other device to finish setup" note (no plaintext
          fallback once a user has keys).
  Step 4  Re-encryption (D-7 option "re-encrypt"): each SENDER's app re-encrypts its
          own v1 messages in batches (rules allow sender-only v1 -> v2 conversion,
          createdAt unchanged). The receiver cannot convert the other person's
          messages. Option "erase": existing erase-for-everyone. Option "keep":
          labelled "Not encrypted" bubbles.
  Step 5  Flip rules to v2-only creates; later remove v1 read compatibility only if
          no v1 docs remain.
  Honest limit: copies of old plaintext may persist in Firestore backups / PITR /
  Google's deletion pipeline for their retention period.

8.9 Interactions with other features
--------------------------------------------------------------------------------
  - Notifications: unchanged and still content-free; functions read only
    senderId/deleted (and never could decrypt).
  - Receipts, typing, presence, calls: unchanged (metadata, not content).
  - Password-only attacker: can sign in and see metadata, delete (unless D-5
    restricts) and place calls, but cannot read or forge messages (forged messages
    fail decryption/AAD). Calls stay a residual risk until SDP signing (8.10).
  - Search: impossible server-side (local only).

8.10 Call signalling authentication (later, Phase 6 / optional)
--------------------------------------------------------------------------------
  Sign the DTLS fingerprint lines of each SDP with the ECDSA identity key; the
  receiver verifies against the trusted peer key before accepting. Files:
  js/calls.js (startCall, acceptCall, watchCallDoc), js/webrtc.js. Rules allow an
  extra 'sig' field on calls.

9. PHOTO UPLOAD ARCHITECTURE
================================================================================

9.1 End-to-end flow (encrypted - matches your intended architecture)
--------------------------------------------------------------------------------
  Sender:
   1. Tap attach icon -> <input type="file" accept="image/jpeg,image/png,image/webp"
      multiple> (gallery / camera roll / file picker).
   2. Client validation per file:
        a) size <= input limit (e.g. 25 MB before processing),
        b) MAGIC BYTES: JPEG FF D8 FF; PNG 89 50 4E 47 0D 0A 1A 0A; WebP "RIFF"....
           "WEBP" (extension and browser MIME are NOT trusted),
        c) decode with createImageBitmap() - must succeed,
        d) pixel limit (e.g. <= 50 MP) to avoid memory exhaustion.
      SVG, GIF, HEIC-as-is, PDF and everything else rejected.
   3. Re-encode on a canvas: long edge <= 2048 px, JPEG quality ~0.85 (PNG kept when
      it has transparency, D-8). This STRIPS EXIF/GPS metadata and neutralises
      polyglot files. Thumbnail: long edge 320 px.
   4. Preview tray under the composer: thumbnails with "x" to remove before sending.
   5. On send, for each photo: new messageId; random fileKey + iv; ciphertext =
      AES-256-GCM(fileKey, iv, imageBytes, AAD "mo|img|<messageId>|<fileId>");
      same for the thumbnail with its own key/iv; sha256 of each ciphertext.
   6. Upload ciphertexts with uploadBytesResumable() to
      att/main/<senderUid>/<messageId>/<fileId>  (contentType application/octet-stream)
      -> progress bar per photo, Cancel = task.cancel(), Retry keeps the encrypted
      blob in memory.
   7. After BOTH uploads succeed, create the message doc (v2) whose ENCRYPTED payload
      contains {fileId, thumbId, key, iv, tIv, sha256, tSha256, w, h, mime, bytes}.
      The other user is notified only now, so no broken images.
  Receiver:
   8. Bubble shows a placeholder; when scrolled into view (IntersectionObserver):
      getBytes() the thumbnail ciphertext -> verify sha256 -> decrypt -> verify magic
      bytes -> Blob(type from allowlist) -> URL.createObjectURL -> <img>.
   9. Tap -> lightbox modal: same for the full image; pinch/zoom by CSS; close.
  10. Object URLs revoked when the bubble is removed and at teardown.

  What Firebase sees: random-looking bytes in Storage, ciphertext in Firestore, the
  storage path (sender UID, messageId), object sizes and timestamps. No pixels, no
  EXIF, no dimensions, no file names.

9.2 Key / IV / tag / metadata handling
--------------------------------------------------------------------------------
  +----------------------+------------------------------------------------------------+
  | Item                 | Where it lives                                             |
  +----------------------+------------------------------------------------------------+
  | fileKey (256-bit)    | Only inside the E2EE-encrypted message payload             |
  | IV (96-bit)          | Inside the encrypted payload (unique per object)           |
  | GCM tag (128-bit)    | Appended to the ciphertext by Web Crypto (integrity)       |
  | sha256(ciphertext)   | Inside the encrypted payload (detects object swap)         |
  | width/height/mime    | Inside the encrypted payload                               |
  | Storage path         | Derivable from senderId + messageId (plaintext metadata)   |
  | Original filename    | Never stored                                               |
  +----------------------+------------------------------------------------------------+
  A per-file key (instead of using the conversation key directly) keeps attachment
  encryption independent of key rotation and allows future forwarding without
  re-uploading.

  index.html  : attach button (new icon in the SVG sprite) left of #message-input;
                hidden file input; preview tray above the composer; lightbox modal.
  css/chat.css: image bubble (max-width ~70% on mobile, 320 px desktop, aspect-ratio

9.4 Limits and trade-offs (D-8)
--------------------------------------------------------------------------------
  - 5 MB processed limit: a 2048 px JPEG is typically 0.3-1.5 MB, so 5 MB is ample;
    larger limits raise Storage/egress cost and memory use (Web Crypto AES-GCM is
    not streaming - the whole file is in memory; phones may fail above ~50 MB).
  - Max 10 photos per send: keeps memory and upload time reasonable.
  - Re-encoding reduces quality slightly and drops metadata (a privacy GAIN).
  - iPhone HEIC: iOS usually converts to JPEG for file inputs that do not accept
    HEIC (NOT VERIFIED on your devices); unsupported results are rejected with a
    message.
  - Saving images to the device writes plaintext outside the app (default OFF).

10. FIREBASE STORAGE INTEGRATION REQUIREMENTS
================================================================================

  E-01  Bucket and plan
        The config names a bucket "<projectId>.firebasestorage.app" (new-style
        default bucket). New-style default buckets require the Blaze plan (needed
        for Functions anyway). Whether the bucket exists: NOT VERIFIED. Create it in
        the console (location close to Firestore). Check current Storage pricing.
  E-02  Initialization
        js/firebase.js: lazy import of
        https://www.gstatic.com/firebasejs/10.12.2/firebase-storage.js and
        getStorage(app) - same pinned SDK version (no new dependency). Loaded only
        after authorization.
  E-03  Security rules: new storage.rules + firebase.json "storage" block + emulator
        port. Rules (illustrative):
          isActive(): request.auth != null
                && request.auth.uid in [UID1, UID2]
                && firestore.get(/databases/(default)/documents/sessions/
                     $(request.auth.uid)).data.authTime == request.auth.token.auth_time
          match /att/{conv}/{senderId}/{messageId}/{fileId}
            read   : isActive() && conv == 'main'
            create : isActive() && conv == 'main' && senderId == request.auth.uid
                     && fileId.matches('^[A-Za-z0-9]{20,32}$')
                     && messageId.size() <= 64
                     && request.resource.size <= MAX (5 MB + 16 B tag + margin)
                     && request.resource.contentType == 'application/octet-stream'
            update : false   (no overwrite of an existing object)
            delete : false   (cleanup by Cloud Functions only - E-06)
          everything else: denied.
        Cross-service rules (firestore.get from Storage rules) need the console to
        grant the Storage rules service access to Firestore (prompt on first deploy)
        and each check costs one Firestore read.
        IMPORTANT LIMIT: because files are encrypted, rules CANNOT verify that the
        object is an image. Type validation happens on the sender (magic bytes +
        decode + re-encode) AND on the receiver after decryption (magic bytes +
        decode). Rules enforce identity, path, size, content type label and no
        overwrite.
  E-04  CORS for downloads
        getBytes()/getBlob() fetch through the SDK (respecting rules) and require a
        CORS policy on the bucket allowing GET from the app origin (gcloud storage
        buckets update --cors-file). Configuration step - NOT done.
  E-05  Download URLs
        Do NOT use getDownloadURL() (long-lived bearer URLs that bypass rules). Use
        getBytes(). Client-SDK uploads may still attach a download token; since the
        object is ciphertext this reveals nothing readable. Optional: a function
        removes the token metadata after upload.
  E-06  Cleanup (Cloud Functions, Admin SDK)
        - onDocumentUpdated(messages): deleted false -> true  => delete prefix
          att/main/<senderId>/<messageId>/.
        - onDocumentDeleted(messages)                          => same.
        - onSchedule daily: delete objects older than 24 h whose message doc does not
          exist (orphans from cancelled/failed sends).
        - "Delete for me" keeps objects (the other user still sees them).
        Note: GCS soft-delete (default 7 days on new buckets) keeps deleted objects
        recoverable by admins for that period - only ciphertext after E2EE.
  E-07  App Check enforcement for Storage (with F-01).
  E-08  Service worker: Storage traffic is cross-origin and never cached by sw.js
        (verified: only same-origin + SDK URLs are cached). No change required.
  E-09  CSP: img-src already allows blob:; connect-src currently "https:" covers
        firebasestorage.googleapis.com; when narrowing (F-06) add it explicitly.
  E-10  Configuration constants in js/firebase-config.js: MAX_IMAGE_BYTES,
        MAX_IMAGE_EDGE, MAX_PHOTOS_PER_SEND, THUMB_EDGE (must match storage.rules).

17. APPENDIX - WHAT CAN AND CANNOT BE HIDDEN (HONEST LIMITS)
================================================================================

Protected against CASUAL viewing (after this plan):
  - Someone opening the site sees an ordinary deals homepage.
  - Wrong credentials show an ordinary member dashboard, no error.
  - Notifications show only neutral, user-chosen text; tapping opens the homepage.
  - Tab title, app name, icons, install name are neutral.
  - With E2EE: Firebase/Google operators, console users and backups see only
    ciphertext for message content and photos.

Still DISCOVERABLE by technical inspection (cannot be fully prevented for a web app):
  - All JavaScript/HTML is downloadable by anyone with the URL (module names like
    chat.js / calls.js, Firestore paths, the chat DOM or template).
  - Network requests show the Firebase project ID ("privatechat-...") unless a new
    project is created (D-2), and Firestore/Storage hostnames.
  - Anything already published in the public GitHub repo (history, README, UIDs,
    rules) may exist in clones, forks, caches and archives.
  - Metadata: who communicates with whom, when, how often, message sizes, presence,
    call times - visible to the service operator even with E2EE.
  - On Android the notification header always shows the app name (or the site
    origin for a browser tab); iOS shows the app name.
  - A compromised or unlocked device, or the other user, can always see content.
  - Whoever controls the hosting or the GitHub/Google accounts can change the code
    that performs encryption (inherent to web-delivered E2EE).
  - A correct password produces a different result (real app or MFA step) than a
    wrong one; the decoy cannot hide that from someone who already knows the
    password.

Not possible in a pure web app:
  - Full-screen ringing call UI when the app is closed (needs a native wrapper).
  - Guaranteed delivery under aggressive OEM battery optimisation or on iOS when
    the system defers pushes.
  - Hiding the app name / origin from the OS notification header.
  - Forcing the earpiece for call audio (documented in README).
